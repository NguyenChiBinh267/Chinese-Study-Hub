# Engineering Loop takeover after baseline acceptance — proposal only

This document changes no controller, configuration, grant, task status or provider. The imported application is existing implementation evidence, not proof that its canonical tasks are DONE. The main controller and its safety policy remain authoritative.

## One initial scope, then dependency-based work selection

After a separately reviewed/authorized baseline merge, reconcile source/main/spec/status/policy hashes and record the accepted baseline. Reuse existing implementation/evidence in bounded task acceptance; do not ask a generator to rebuild the whole app or replay157 commits.

The owner can authorize **one bounded release scope** rather than assign every next task. That initial grant must identify permitted task IDs/instances, allowed paths, expiry, call/time/repair limits, ordinary-account quota reserve, exact source/policy binding, stop conditions and explicit merge/status permissions. It must be owner-supplied/approved; the agent cannot manufacture it.

Within that scope, the existing driver selects dependency-ready tasks from Git SSOT, then runs separate Developer→deterministic checks→read-only Reviewer→at most two repairs. Persisted grant identity, budgets, deadlines and recovery checkpoints continue to apply. Missing human evidence can block that task while independent eligible tasks proceed only as the configured driver allows. No paid/provider fallback or automatic rights/language attestation is introduced.

The owner does not need to issue a new assignment for each eligible task. Human account/legal/rights/competent-review facts still require real evidence; batch those receipts with exact scope/bytes/expiry where valid. A stop for missing human facts is not a request to manually choose the next task, and cannot be bypassed with an AI declaration.

## Conditions that must precede activation

1. Accept/review/merge the baseline through the separately authorized process. Recheck any advanced main and preserve its newer Loop/SSOT files.
2. Resolve main's recorded Loop readiness blockers. The preserved main documentation distinguishes approved routing assurance from actual-model verification and retains historical unresolved diagnostic/full-candidate-review gates. This integration does not run a new smoke, rewrite old results or assert those gates passed.
3. Define reviewed acceptance policies and bounded instances for the permitted task set. Existing configuration policies are not a general license for all70 tasks. Select from the dependency-ready DAG; do not jump to T009/T026/T052 because code exists. Materialize authoring instances and retain later-release activation boundaries.
4. Run a fresh exact-SHA bootstrap/reviewer process only when its real source/account/quota/policy gates and explicit authorization permit it. Manual subagent review here is not that process.
5. Set runtime controls only under the accepted grant. Keep live/authorized-task/auto-merge/status-write authority inactive now. Do not copy old private grants, synthetic D004 state or stale receipts into the new authority path.

## What happens at merge/status boundaries

If a future grant includes bounded controller merge/status authority, retain exact reviewed SHA, pinned parent/tree, non-force publication, persisted intent/replay protection and single-task remote readback before DONE. An advanced source/main, expired grant, exhausted budget, stale review or unsafe scope stops/reconciles the run.

If future policy keeps `autoMerge=false`, the controller can prepare reviewed PRs but stops at its merge boundary. Do not describe that mode as an unattended end-to-end merge loop. The present task grants no push/merge/deploy or status authority; no flags are enabled here.

## Suggested first acceptance work

Use fresh baseline evidence to scope the actually ready M0 tasks and repair gaps, preserving official dependencies. Local schema/RLS/proof and core browser checks support evidence for relevant interfaces; they do not complete T009/T026/T052. Free-account/host tasks retain real owner/account/benchmark gates; source learning material stays DRAFT until its own rights/competent-review/publication gates are met. HSK1 curriculum completion and new content are not the next implicit task.

This is a proposed operating model grounded in the existing driver. It is not a new scheduler, a real Loop run, an owner grant or a promise that current readiness blockers are already solved.
